# Standup-отчёт

Собери, что было сделано за отчётный день, и выведи короткий отчёт. Skill только читает историю — ничего не коммить, не пушь и не меняй файлы.

## 1. Определить отчётный день

- Если передан аргумент `$ARGUMENTS` в формате `YYYY-MM-DD` — отчётный день он.
- Иначе — вчерашний день по локальному времени:
  ```bash
  date -v-1d +%F 2>/dev/null || date -d yesterday +%F
  ```

Дальше `<DAY>` — отчётный день.

## 2. Собрать данные

```bash
git config user.email
git fetch origin --prune
```

**Коммиты** за день во всех ветках (включая удалённые — ветки после merge удаляются):

```bash
git log --all --no-merges --author="<email>" \
  --since="<DAY> 00:00" \
  --date=format-local:'%Y-%m-%d %H:%M' \
  --format='%H%x09%ad%x09%D%x09%s'
```

`--since` фильтрует по дате коммиттера и отдаёт коммиты с запасом (в том числе более поздние). Из вывода бери только строки, где дата автора (второй столбец) начинается с `<DAY>`: после rebase дата коммиттера сдвигается, а дата автора — нет. Команду запускай как есть, без pipe в `awk`/`grep` — они не входят в `allowed-tools`.

- Одна и та же работа может встречаться несколько раз: коммит в рабочей ветке и его squash-коммит в `master` (subject с суффиксом ` (#N)`), копии после rebase. Коммиты с одинаковым subject (без учёта ` (#N)`) считай одним.
- Чтобы понять суть изменений, а не пересказывать заголовки, смотри тело коммита и затронутые области: `git show --stat --format='%B' <hash>`.

**Pull Request'ы** (если `gh` не авторизован — опирайся только на коммиты):

```bash
gh pr list --state all --author @me --search "updated:<DAY>" \
  --json number,title,state,createdAt,mergedAt,body
gh search prs --reviewed-by @me --updated <DAY> \
  --json number,title,state,author
```

Если за `<DAY>` нет ни коммитов, ни активности в PR — так и скажи и предложи указать другую дату (`/standup YYYY-MM-DD`). Ничего не выдумывай.

## 3. Сформировать отчёт

Отчёт — **1–3 коротких абзаца** обычным текстом на русском, который можно зачитать или вставить в чат команды. Заголовок — одна строка с датой, например `**Стендап за 18 сентября 2026**`.

- Передавай общую суть: какие задачи двигались, что в итоге появилось или изменилось в продукте или процессе и зачем. Связанные коммиты объединяй в одну мысль.
- Упоминай статус задач: слито в `master`, открыт PR на ревью, ещё в работе. Номер PR — по желанию, коротко (`PR #7`).
- **Не выводи** список коммитов, хеши, пути и имена файлов, построчные перечни изменений.
- Ревью чужих PR, если они были, — одной фразой.
- Планы и блокеры не придумывай; упоминай только незавершённое, что видно из данных (открытые PR, неслитые ветки).
