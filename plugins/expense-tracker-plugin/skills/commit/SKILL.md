# Коммит в ветку

Правила коммитов проекта и порядок действий. Выполняй шаги по порядку; если шаг не проходит — остановись и сообщи пользователю, не обходи проверку.

## Текущее состояние репозитория

Снимок на момент вызова skill — используй его вместо повторного запуска этих команд в шагах 1–2. После любых изменений рабочего дерева (создание ветки, проверки, `git add`) состояние нужно смотреть заново.

- Текущая ветка: !`git branch --show-current`
- Статус:
  !`git status --short --branch`
- Изменения в индексе (staged):
  !`git diff --staged --stat`
- Изменения вне индекса (unstaged):
  !`git diff --stat`
- Коммиты ветки относительно `origin/master`:
  !`git log --oneline origin/master..HEAD`
- Последние коммиты (для ориентира по стилю сообщений):
  !`git log --oneline -5`

## 1. Проверить ветку

Текущая ветка и статус — в блоке «Текущее состояние репозитория».

- Напрямую в `master` не коммитим. Если текущая ветка `master` — создай ветку под задачу от актуального `origin/master`:
  ```bash
  git fetch origin master
  git switch -c <type>/<scope>-<краткое-описание> --no-track origin/master
  ```
  - Незакоммиченные изменения должны перейти в новую ветку вместе с `git switch -c`.
  - Если Git не даёт создать ветку из-за конфликтующих локальных изменений — остановись и сообщи пользователю.
  - Не выполняй автоматически `git stash`, `git reset`, удаление файлов или другие потенциально разрушающие операции без явного разрешения пользователя.
- Если уже на рабочей ветке — убедись, что изменения относятся к её задаче. Одна ветка — одна фича/задача; посторонние правки — в отдельную ветку.

**Именование веток**: `<type>/<scope>-<краткое-описание>` — латиницей, kebab-case, `type` из того же списка, что и в коммитах (см. ниже):

- `feat/frontend-home-page` — новая фича
- `fix/auth-token-refresh` — исправление бага
- `refactor/transactions-service`, `docs/readme-setup`, `chore/eslint-config`

## 2. Разобрать изменения

Список изменённых файлов — в блоке «Текущее состояние репозитория». Содержимое изменений посмотри через `git diff` / `git diff --staged` (для нужных файлов — `git diff -- <path>`); если ветка создавалась в шаге 1 — сначала заново `git status`.

- Один коммит — одна логическая единица (фича, фикс). Не смешивать фичу с посторонними правками. Если в рабочем дереве несколько несвязанных изменений — разбей на несколько коммитов (или вынеси лишнее в другую ветку).
- Миграция Prisma (`apps/backend/prisma/migrations/`) коммитится в том же коммите, что и изменение `schema.prisma`.
- **Не коммитить** `.env*` (кроме `.env.example`) и `.claude/settings.local.json`.
- Добавляй файлы явно по путям (`git add <path>...`), а не `git add -A` / `git add .`, чтобы не захватить лишнее.

## 3. Прогнать проверки

Из корня монорепозитория, перед коммитом должны пройти все три:

```bash
npm run typecheck
npm run lint
npm run build
```

CI эти проверки не запускает — ответственность на авторе. Если что-то падает — исправь (если это часть задачи) или сообщи пользователю; не коммить с падающими проверками и не используй `--no-verify`.

После успешных проверок повторно посмотри состояние рабочего дерева:

```bash
git status
git diff
git diff --staged
```

Убедись, что `lint`, `build` или другие проверки не создали и не изменили файлы, которые не должны попасть в коммит. Такие файлы в коммит не добавляй; если непонятно, откуда изменения, — сообщи пользователю.

## 4. Составить сообщение

Коммиты оформляются по [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <описание>

- что сделано и зачем (опционально, списком)
```

- **type**: `feat` — новая функциональность, `fix` — исправление бага, `refactor` — рефакторинг без изменения поведения, `perf` — производительность, `docs` — документация, `style` — форматирование, `test` — тесты, `build` — сборка и зависимости, `ci` — CI, `chore` — прочее (конфиги, служебные файлы)
  - Тип основного коммита должен совпадать с типом в имени ветки (`chore/...` → `chore(...)`): PR сливается squash'ем, и заголовок PR повторяет этот коммит. Перед коммитом сверь тип с `git branch --show-current`. Если тип изменений не совпадает с веткой — остановись и выбери один вариант: поправь тип коммита или (если ветка ещё не запушена) переименуй ветку, а посторонние изменения вынеси в отдельную ветку
- **scope** (опционально): модуль или слайс, который затрагивает изменение — `transactions`, `categories`, `auth`, `frontend`, `prisma` и т.п.
- **описание**: на русском, в инфинитиве («добавить», «исправить»), с маленькой буквы, без точки в конце, до ~72 символов
- **тело**: через пустую строку, коротким списком — что изменилось и почему
- **breaking change**: знак ! после scope (`feat(auth)!: ...`) и футер `BREAKING CHANGE: <что сломалось>`

Пример:
```
feat(transactions): добавить модуль учёта доходов и расходов

- модель Transaction и миграция add-transactions
- CRUD /transactions с фильтрами и сводкой /transactions/summary
- запрет удаления категории с транзакциями (409)
```

## 5. Закоммитить

Сообщение передавай через heredoc, чтобы сохранить переносы строк:

```bash
git add <paths>
git commit -m "$(cat <<'EOF'
<type>(<scope>): <описание>

- ...
EOF
)"
git log -1 --stat
```

После коммита покажи пользователю ветку, сообщение и список файлов. `git push` и создание PR — только если пользователь попросил (правила PR — в корневом `CLAUDE.md`).
